# Design Build

Read the shared [design contract](../design/references/design-contract.md), [design principles](../design/references/design-principles.md), [quality](../design/references/quality.md), and relevant [integrations](../design/references/integrations.md). Confirm the complete available Dev suite and explicitly read its discovered `dev-build` entry point before any production source edit, including CSS. Apply its shared contracts and validation ownership; Design does not replace Dev.

## Build The Accepted Direction

Inspect the actual project, relevant interface, existing documentation, tokens, components, and assets. Establish the task and affected states. If intent is consequentially ambiguous, explicitly read [design-intent](../design-intent/SKILL.md) and resolve the dependent choice through its question procedure. Use [design](../design/SKILL.md)'s shape mode only when direction needs work; a small settled edit reuses its established direction.

Reuse project and platform capabilities before adding a mechanism. Use relevant discovered design, motion, and browser guidance without treating every upstream workflow as mandatory. Apply hierarchy, proximity, alignment, repetition, contrast, typography, and color to identifiable task needs. Preserve explicit style constraints; polish does not imply a hero, effects, new features, or a different product.

Implement the coherent requested scope under Dev, including necessary callers and states. Run suitable existing checks and inspect the rendered result and affected interactions with available capabilities. When new or semantically changed validation is necessary, use discovered `dev-test` and Dev's distinct compatible Tester; do not author correctness scripts, assertions, or fixtures in the Developer role. Observation and existing checks need no new Tester.

## Inspect And Improve

Self-inspect against the applicable award-level quality standard and relevant benchmarks. Repeatedly improve an identifiable material gap: observed gap → supported cause → scoped change → actual affected checks. Revisit the diagnosis when iterations stagnate. There is no fixed polishing-round cap; the agent decides from evidence when the quality completion rule is met, without mandatory user grading or a separate design reviewer.

Recheck the latest changes and important affected states. Finish only when the requested behavior and scope, functional/quality floor, and relevant benchmark standard are evidenced, with no unresolved material quality gap, important regression, or critical unknown. Report the concrete result, meaningful evidence and its boundary, and any remaining delivery step. Missing access, assets, environment, or budget leaves work accurately unfinished; do not lower the standard or claim an unobserved result.
