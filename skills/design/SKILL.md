# Design

Deliver the requested design outcome through the relevant mode. Read the shared [design contract](references/design-contract.md) first; sibling names do not inherit instructions.

## Route By Outcome

Explicitly read a selected entry point before applying it. Do not pass simple work through every mode.

| Requested outcome | Mode |
|---|---|
| Name a concept, translate rough wording, or resolve consequential ambiguity | [design-intent](../design-intent/SKILL.md); may finish standalone in any domain |
| Shape an interface's hierarchy, visual direction, or interaction plan | Shape here; read [design principles](references/design-principles.md), [quality](references/quality.md), and relevant [integrations](references/integrations.md) |
| Build, fix, or polish production interface source, including CSS | [design-build](../design-build/SKILL.md) |
| Inspect an interface or critique a direction without changing source | [design-review](../design-review/SKILL.md) |

For mixed work, keep one accepted intent and use only the needed modes. Terminology outside design stays in its domain; it is not an instruction to build a frontend.

## Shape

Inspect existing project guidance, content, tokens, assets, and the relevant interface. Establish the audience, main task, constraints, and meaningful states; revisit consequential ambiguity through Design Intent before choosing dependent direction. Reuse the established direction for a small change. For a new direction, select relevant product/platform references and explain the choices that affect the task: hierarchy, composition, typography, color, imagery, interaction, and motion where useful.

Use the two-book principles as decision and evidence tools, not a list of slogans. Show or describe enough of the proposed direction to make the important choices reviewable; multiple variants or a prototype are useful only when they resolve a real choice. Do not create mandatory parallel design documents or manufacture approval gates. A plan or mockup must be labeled as such; it does not prove runtime usability or production quality. Continue authorized implementation through Design Build when requested.

Report the direction, decisive evidence, preserved constraints, and unresolved choices in the form the task needs. Apply the quality completion rule to the actual deliverable and state what remains unobserved.
