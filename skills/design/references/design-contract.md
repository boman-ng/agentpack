# Design Contract

The complete suite contains sibling `design`, `design-intent`, `design-build`, and `design-review` skills and their resources. Confirm entrypoints and required files once per task; report missing resources. Each direct entry loads its relevant shared resources, without rereading those already loaded.

## Intent And Scope

Preserve the user's goal, language, brand/style constraints, content, and anti-goals. Distinguish confirmed intent from observations, interpretations, examples, and proposals when the difference affects a choice. Use project-owned docs, tokens, components, and assets; no mandatory design state file is needed.

For ambiguity that changes the outcome, read [Design Intent's clarification flow](../../design-intent/SKILL.md#clarification-flow) before dependent actions. It owns questioning, HTML delivery, answers, corrections, and fallback for all Design modes. Clear terminology and settled edits proceed directly; continue independent work while a choice remains unresolved.

## Integrations And Quality

Follow [runtime integrations](integrations.md) for external skills and Dev ownership of production changes and new validation. Skill selection does not authorize installations, accounts, settings, publication, or other external side effects. User instructions take precedence over conflicting skill guidance within host constraints; disclose material conflicts.

For shaping, building, or reviewing interfaces, apply [quality and completion](quality.md). Standalone terminology does not invoke the frontend quality workflow. Inspect supplied artifacts before claiming observations; use [visual evidence](../../design-intent/references/visual-evidence.md) when the material's limits affect interpretation.
